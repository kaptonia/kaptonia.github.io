Command line

The app comes with a command line, zikaron: one subcommand per operation, each printing one JSON value on standard output, with the outcome in its exit code. It works in two ways: alongside the desktop, or on its own.

Putting it in the terminal

Turn on “Enable command line” in Settings › Local data, and zikaron works in any terminal. Installed from the .pkg or .deb, it already does; with the AppImage, install the .deb for the command line. On Windows, zikaron.exe runs in a terminal.

Run zikaron contract for every subcommand, its flags and the exit codes. How to write each command is in Developer guide · Command line.

Way one: alongside the desktop

While the desktop is open and unlocked, a command carrying your data folder, --home "<data folder>", is handed to the running ZIKARON Desk. The desktop signs as you and writes to its ledger, along the same path as your own clicks: the same checks, the same messages, the window updating at once. The private keys and the passcode stay in the desktop the whole time; the command line only hands over requests.

  • Where the data folder is: under “Details” in Settings › Local data, the “Data folder” row gives the path of this role’s data folder for the current identity.
  • Read-only work: checking other people’s material and other read-only work the command line does directly.
  • Work on the desktop: setting the passcode, managing keys, whole-machine backups and anything that asks for the passcode are done on the desktop.
  • When the channel is open: the local channel is open to you on this computer alone, and only while the desktop is unlocked and holding this data folder; locking, closing the data folder or quitting shuts it, and the command line gets exit code 4.

Two modes for putting on chain. When the command line asks the desktop to put entries on chain, “Putting on chain from the command line” in Settings › Network decides:

Send automatically
The default. The desktop sends everything sendable in the queue as one batch, the way “Put all on chain” does, paying the fee from this identity’s address. In a block within 30 seconds, the command line hands back the block number and transaction hash; while it is still waiting, the command line answers that the transaction is still outside a block (exit code 4), and the desktop keeps waiting for the receipt.
Queue only
The desktop keeps the entries in the queue, and the command line answers “Queued; waiting for the user to send it from the desktop” (exit code 3). The desktop shows the toast “N records from the command line are queued” and alerts you once; you check them on the desktop and press “Confirm and send”.

Way two: the command line on its own

The command line can start from nothing by itself, with no desktop and no graphical interface:

  1. Make a key. In your own terminal, run zikaron keygen, which prints a new address and its private key. Save the private key alone in a file, set so only you can read it (chmod 600 on macOS and Linux), and point later commands at it with --key-file.
  2. Add gas. Send a little ETH to that address.
  3. Create a ledger. zikaron init --ledger "<ledger folder>" --key-file "<key file>" --statement "<description>". Later writes, such as records, grants, revocations and notes, carry those two and go into this ledger folder.
  4. Put on chain. anchor takes the node with --endpoint, the registry contract with --registry (on Ethereum mainnet, 0x36Ea8A857a5FE813429d4D9947000C644A88809A) and the entry IDs to anchor with --hash, which can repeat, so one transaction anchors several. Running the same command again first asks after the transactions it already signed, so one anchoring is paid for once.
  5. Check and present. scan and audit check the ledger against the chain, kit-export exports a record kit, and check-grant verifies a grant.

The ledger it writes is the same format the desktop writes, and anyone can verify it with the desktop app or the command line. To bring this ledger into the desktop later, import the private key with “Import key…”, then use “Adopt in place” under “Advanced options” in Settings › Local data.

Plain files

With the command line on its own, these sit on disk as plain files:

FileWhat it holds
The key fileThe key itself. Whoever has it can sign any entry as you and spend the ETH at the address
The ledger folderEvery entry, content meant to be handed to others for checking anyway; change one byte of an entry and its signature fails
cli-sent/Hashes of the transactions the command line signed

The key file is what matters. Anyone or any program that can read files as this system account can read it, so keep it this way:

  • Small funds, a ledger of its own. Use this key for this purpose alone, with only enough ETH at its address for gas, apart from your main identity.
  • Guard the system account. Turn on the system’s full-disk encryption; allow remote logins by key alone.
  • Hand the key to the command line by file alone. Give it with --key-file; the command line takes a key file only you can read. Keep the file outside synced folders and automatic backup folders, with one more copy somewhere safe and offline.
  • Prefer the desktop. Alongside the desktop, the key stays in the desktop’s key store, encrypted under the passcode. Keep the command line on its own for when a machine with no screen is truly needed.

What the command line answers

Exit codeMeaning
0Done, or the check passed
1Refused, or the check failed; the reason is in the output
2The command is wrong; standard output is empty
3A partial result (some checks still await an answer), or queued for you to send from the desktop
4No answer: none from the desktop (quit, locked, or holding another data folder), nodes unreachable, or the transaction still outside a block
