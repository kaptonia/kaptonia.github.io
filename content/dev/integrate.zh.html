让你的应用读取 {{Z}} 的记录：核验授权、读取记录包、请用户的桌面应用代写条目，或在业务流程中提示用户留证。

接入方式

接入有两条路。多数应用是读者：读者拿到的是用户导出的成品，授权码、授权文件、记录包。要在业务流程里替用户留证的应用，可以经桌面写入：以 --home 调用 zikaron，由用户正在运行的 {{Z}} 在它的数据目录里代写条目或上链，见经桌面写入。两条路下，一本账本都只有一个写入者，密钥也只在一处。

用命令行核验

最简便的接入方式是以子进程调用 zikaron，读取其退出码与标准输出。

{{code: zikaron check-grant --grant grant.entry --ledger ./issuer-ledger \ --fragment fragment.json --now $(date +%s) }}
退出码应用的处理
0放行
1拒绝。核验失败时列出失败的项；授权文件拆不开(E_GRANT_FILE)、账本或输入有误时显示原因
3暂缓。告知用户哪一项尚待结果，稍后重试
4答案缺席：节点不通、各节点答得不一致、扫描被拒，或取不到随机数；经桌面时桌面缺席。重试，或更换节点
2调用有误，请检查参数。标准输出为空；标准错误的第一行是 <原因> <对象>，只认这一行，第二行起是给人看的话，随系统语言显示中文或英文

--grant 收一个授权条目文件，也收用户导出的授权文件 .zkgrant：命令行按应用的同一读法拆开，核的是这份文件为之而立的那一跳。授权码的每一段是条目字节的 base64url 编码(省去填充)，解码后存为文件即可；多段的授权码(转授权链)用 chain-check --hop 逐跳核验。--ledger 可以直接指向用户导出的账本镜像或记录包，见命令行。节点地址可以是 http:// 或 https://；连节点的 scan 与 anchor 收 --proxy(system、none 或一个代理地址)，缺省跟随系统代理，本机上的节点一律直连。

要核对你的调用与所装版本是否对得上，跑 zikaron contract：它把动词、参数、退出码与拒因输出成一个 JSON 值，由代码里的同一张表生成。

请把 3 作为独立的一档处理：「暂无结果」「通过」「失败」是三种状态，界面上也以三种样式呈现。

经桌面写入

给 --home <桌面的数据目录> 时，十一个写入动词(init、history、grant、revoke、adopt、attest、succeed、annotate、retract、anchor、kit-export)交给正在运行、已解锁、并以写者打开这个数据目录的 {{Z}} 去做：条目以用户的身份写进用户的账本，窗口里随即可见。私钥与口令都留在桌面里。

{{code: zikaron history --home "$DESK_HOME" --file ./delivery.pdf --note "交付第一版" }}
答复应用的处理
0写成。输出带 entryId 与 seq，存下编号以便日后指向这条记录
E_DESKTOP(4)以写者打开这个数据目录的桌面此刻缺席：已退出、已锁定，或开着别的数据目录。请用户打开并解锁 {{Z}} 后重试
E_QUEUED(3)anchor 时用户把「命令行上链」设成了「仅加入队列」：条目已排进队列，等用户在桌面上发出
E_DESKTOP_REFUSED(1 或 4)桌面具名拒绝，token 是它的代码；网络方面的拒绝为 4
E_ON_DESKTOP(1)attest 要口令，只能在桌面上做

这条路只通本机本用户：通道是机器目录里只本人可读写的套接字文件，或只本用户可连的命名管道，两端各自向系统核对对方是谁。桌面锁定、关闭数据目录或退出，通道即关。各动词带 --home 时收哪些参数，见命令行 · 经桌面。

直接调用核

Rust 项目可依赖 zikaron 与 zikaron-kit 两个 crate。它们只做判断：链由你的代码去读，再把字节交给核；记录包目录可以交给 zikaron_kit::kitdir::verify_kit 直接从盘上读取核验。其他语言请依据法文自行实现，并用一致性套件验收，见测试一份实现。

读取用户导出的记录包

同一台机器上的应用可以列出用户已导出的记录包，供用户选择递交。机器目录按应用自己的顺序找：

  1. 用户在你的应用设置中手动指定的目录。
  2. 指针文件中写明的路径：macOS 与 Linux 上是 ~/.zikaron-desk，Windows 上是 %LOCALAPPDATA%\ZIKARON\.zikaron-desk(环境变量 USERPROFILE 指向别的文件夹时，改为它下面的 AppData\Local\ZIKARON\.zikaron-desk)。指针存在时以它为准：目标读取失败，请明确告知用户「{{Z}} 的数据已迁移」，并请其重新指定。
  3. 指针缺席时：macOS 上先看 ~/Library/Application Support/ZIKARON(存在时)；其次是默认位置，macOS 与 Linux 上 ~/.zikaron-desk.d/，Windows 上 %LOCALAPPDATA%\ZIKARON\.zikaron-desk.d\。

「有效」的唯一标准：该处的 kits/index.json 可读，且格式名为 zikaron.kits-index/1。

索引行的 anchoredOn 写明这个包锚在哪条链(链号、登记合约、起始区块)。用户在 {{Z}} 里核验过的记录包，机器目录的 kits/verified/<包编号>.json 里有一份核验结果档：包成不成立、每件记录最早计入的锚、这一次读成与没读成的网络，格式见核验结果档。只读这份档、自己不读链的应用，由它得知记录包锚在哪条链、成不成立。

你的应用对 {{Z}} 数据的权限限于读取：机器目录里的 kits/index.json 与 kits/verified/，以及索引行 path 指向的记录包文件夹(它们在各数据目录的 kits/ 下)。拿到记录包后先自行核验，再使用其中的文件。

让记录指向你的交易

用户为你应用中的一笔交易留证时，可在「为谁留证(可选)」中填写你的应用名、对方身份、对方编号，以及可选的对方角色，这些内容原样写入条目的 for 成员(角色存为 seat)；对方身份须为 0x 加 40 位十六进制。日后读到这条记录的人，据此对应到具体交易。

请在界面中列出这几个值，便于用户照抄：应用名用固定的短字符串，编号用你系统中该笔交易的编号。

在关键时刻提醒

事前留下的记录分量最重。请在流程中找出这些时刻并提醒用户留证：交付文件时、确认收货时、双方就条款达成一致时。

签名请求

需要用户签名时，请让用户使用交易密钥。身份密钥专用于账本；{{Z}} 的界面也照此设计，签名只发生在用户自己发起的写入中。

约定新的条目类型

条目类型是开放的。你可以约定一种新类型，写明类型名、正文成员与读法，并公开这份约定。其他读者遇到它时列入「无法识别的类型」，法的检查结论照旧；ZIKARON Desk 的账本状态行会把它算作问题。

  • 类型名选用带项目前缀的字面量，与现有类型区分开。
  • 正文引用其他条目时，使用条目编号。
  • 读法写成对全部输入都有定义的规则：格式相符时如何读，格式有误时如何显示。
  • 把约定登记在仓库的讨论区，便于其他实现采纳。
