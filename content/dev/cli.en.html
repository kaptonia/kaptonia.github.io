zikaron offers the same ledger operations as the window, one subcommand per action. It is built for scripts: the output is a single JSON value, and the verdict is in the exit code. The full output shapes, exit codes, refusal reasons and flags are in CLI-SCHEMA.md in the source.

target/release/zikaron

Three conventions

Standard output is one canonical JSON value
Each call prints one value, ending at the value’s last character. The byte format follows law §3.4: compact, members sorted by bytes.
Misuse leaves standard output empty
For wrong arguments or an unreadable path, the exit code is 2, standard output has zero bytes, and the first line of standard error reads <reason> <subject>, as in E_UNREADABLE /nowhere/at/all, the subject being only the flag, value or path at fault; a second line explains it for people and is outside the contract. Whether standard output holds any bytes tells a caller an answer from a misuse.
Status words pass through unchanged
GREEN, PARTIAL, FAIL, COMPLETE, GAPS and the like are written by the cores and passed on by the command line as they are.

When the law refuses an entry being written (E_ENTRY with the token E_BODY_FIELD, exit code 1), standard error carries one more line for people, naming the member and the flag that gives it, for example mode: 缺或不成形,由 --mark 与 --toolchain(或 --file) 给; this line is outside the contract too, and standard output and the exit code are the same with or without it.

Files are written one way: --out first writes a whole temporary file alongside, syncs it to disk, then renames it into place; when a file of that name already exists, the write stops and the existing file keeps every byte.

Exit codes

CodeMeaningExample
0Answered, affirmativeGREEN, COMPLETE
1Answered, negativeThe entry was refused, the write would break the ledger (E_WOULD_BREAK), the node says the transaction would fail or estimates it above 200,000 (E_GAS_REFUSED), a grant file does not open (E_GRANT_FILE), a record kit does not hold (E_KIT), or the verdict is FAIL, BROKEN_CHAIN or NO_LABEL
2MisuseWrong arguments or an unreadable path; standard output is empty
3Answered, in betweenPARTIAL, GAPS, UNAVAILABLE
4Answer absentNode unreachable, nodes disagreeing, scan refused, no randomness available

The weight of this table is that 3 and 4 each have a code of their own. Fold “not yet on chain” into 0, and a buyer takes an unanchored grant as cleared; fold it into 1, and a passing “not yet known” reads as “forged”. Fold “node unreachable” into 1, and a network fault reads as “this chain is fake”. A failed scan is an absent answer, and the caller retries or changes nodes.

Any other first word counts as misuse, with exit code 2.

Flags

All fifty-three flags are long flags, and each takes a value; every subcommand has its own table of flags, and a flag outside it counts as misuse. Members the law requires in an entry’s body may all be left off the command line; the core then refuses the entry under the law, and the command line checks the few items it needs for its own work. That way each rule of judgment exists once, in the core. Each subcommand’s flags and the environment variables (the chain-read timeout ZKA_TIMEOUT_SECS, 30 seconds by default; the answer limit ZKA_MAX_ANSWER_BYTES, 64 MiB by default; and so on) are listed in CLI-SCHEMA.md.

Example

Generate a key, create a ledger, record a file, anchor it, audit:

{{code: zikaron keygen # {"address":"0x…","ok":true,"privkey":"0x…"} zikaron init --ledger ./ledger --key --statement "Records of my work" zikaron history --ledger ./ledger --key --file manuscript.pdf # {"entryId":"0x…","ledger":"…","ok":true,"seq":1,"written":true} zikaron anchor --key --endpoint = \ --form registry --registry --hash zikaron scan --endpoint = --endpoint = \ --basis basis.json > fragment.json zikaron audit --ledger ./ledger --fragment fragment.json echo $? }}

history --file fills the entry by the convention the app uses to record a file: content is the SHA-256 of the file’s bytes, and mode is {"mark":"bytes-sha256/1","toolchain":<the SHA-256 of the text "bytes-sha256/1">}; for one file, the command line and the app write these two members alike. You can also leave out --file and give --content, --mark and --toolchain yourself; the two ways cannot be mixed.

Node addresses may be http:// or https://, in any case; https checks the certificate chain and host name against the roots compiled into the program, the same transport the app uses. anchor takes exactly one --endpoint: it reads that node’s base fee and the paid tips of the last 20 blocks, sets the fee by the app’s rule, then asks the node to estimate gas for this very transaction and carries one and a half times the estimate, rounded up, at most 200,000; if the node says the transaction would fail or estimates it above 200,000, it refuses with E_GAS_REFUSED, and if the node does not answer, it reports E_UNREACHABLE; either way nothing is sent. Once sent, it asks for the receipt round after round until --wait-secs runs out.

Each question scan asks names the senders in the scan range, so only their logs come back; when a node declines, the same question is asked again, and only after three refusals is the range split. basis.json states the scan range: which chains, which registry contract, which senders, and the start and end blocks; the format is in law §9.4. The command line keeps no record of facts checked before, and every scan asks about every log.

Audited before written

Every subcommand that writes an entry (init and retract included) passes through one gate: once the entry is signed, the core audits “this ledger plus this entry” offline, and any chain finding of law §8.3 the ledger did not already have (an old key writing after a key change, a sequence gap, a second entry at one place, a link to the wrong entry) refuses the write with E_WOULD_BREAK, names listing the findings, and not one byte is written. --seq and --prev given by hand pass the same gate. When a ledger holds two roots and no --root is given, every write is refused with E_TIP_FORKED.

Time is injected by the caller

Deadlines and periods are judged by chain time and the moment injected with --now; when --now is left off, chain time alone applies. Every moment comes from the caller, so the same input always reaches the same verdict.

Reading the app’s own ledger

A ledger in ZIKARON Desk’s data folder is encrypted and the passcode lives in the app, so the command line refuses it as misuse, with exit code 2 and these lines on standard error (the second reads “locked: this is ZIKARON Desk’s sealed local data; the command line does not read it”):

{{code: E_UNREADABLE 已锁定:这是 ZIKARON Desk 封存的本机数据,命令行不读 }}

To hand a ledger to the command line, export a “Ledger mirror” or a “Record kit” in the app first. The --ledger of audit (and, through it, check-grant, chain-check and depth) and of show --entry can point straight at the mirror folder (the level holding mirror.json) or the kit folder; a kit is first checked under the kit law and refused with E_KIT if it does not hold. The subcommands that write entries, and init, take ledger folders alone: to carry on writing, copy the files in the mirror’s entries/ into an empty folder and add .entry to each file name.
