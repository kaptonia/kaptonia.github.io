Four layers

  1. Base (base/). Law texts, frozen cores, corpora, the contract, chain-facing fixtures: the reference for everything else. The frozen cores are pinned by the digests the law texts name, and the contract by its code hash; the rest is tooling, free to rebuild, replace or delete.
  2. Cores and storage (zikaron, zikaron-kit, zikaron-store, zikaron-anchor, with zikaron-net and zikaron-os beneath them). Every judgment is made here. The two cores depend on no other workspace crate; nodes are reached through zikaron-net alone, and system randomness, owner-only files, syncing to disk and replacing renames come from zikaron-os, which storage, glue, the command line and the app all go through. The app’s own system-dependent pieces (file dialogs, the write lock, the home folder, the time zone, Chinese fonts and so on) live in crates/app/src/platform/.
  3. Glue (zikaron-cli, zikaron-glue). Assembles inputs, calls the cores, passes results on unchanged.
  4. Interface (zikaron-ui, app). Presentation and interaction.

Dependencies point downward: an upper layer calls the public interface of a lower one, and lower layers stand independent of upper ones. Every crate is written from the law texts on its own, with zero path dependencies on base/. zikaron-pack stands outside the four layers: it is the app’s build dependency and the packaging tool, uses the standard library alone, and nothing depends on it at run time.

Five rules

The interface only presents
Whether an entry is valid and whether a grant is in force are concluded by the cores, and the interface presents the conclusion. Interface code that judges syntax for itself belongs in a core.
The glue only assembles
The command line and glue code turn arguments into inputs, call the cores and choose the exit code; bytes a core writes are passed on as they are, keys and values unchanged.
The criteria stay as they are
The two frozen cores are pinned by the digests in the law texts, and the registry contract by its code hash; those bytes stay as they are. Raise objections to them as issues; see Compatibility and evolution.
Verify pages only read the chain
Verify grant, Verify record and Look up a ledger read their inputs and the chain and send not a single transaction; what they write on this machine is the address book, snapshots and verification result files.
Identity keys sign the ledger alone
Keys in the app sign entries, co-sign for adoptions and send anchoring transactions; payments, wallets and delegation are left to other software.

One implementation, reused everywhere

Each judgment is implemented once. The six checks on a grant come from zikaron-kit, shared by the verify page, the command line and the periodic review of My grants; the readings likewise. The app and the command line also share how a grant file is read (zikaron_glue::grantfile), the ledger mirror layout (zikaron_glue::mirror), the convention for recording a file (zikaron_glue::recording, which history --file uses), the fee and gas-estimate rules (zikaron-anchor), and the single TLS configuration (zikaron-net). The same input therefore gets the same verdict at every entry point.

Every type of ledger entry has a subcommand that writes it. When adding an action to the app, make it work on the command line first, then build the interface.

Law citations in comments

Code comments cite zikaron/1 as law §N (on the kit side also parent law §N) and zikaron.kit/1 as kit law §N. Before changing an implementation, read the section it cites.
