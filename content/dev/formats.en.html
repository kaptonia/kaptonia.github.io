The kinds of file the app and the command line read and write. Versioned formats carry their version inside the file.

Entries

An entry is a canonical JSON object with exactly seven members:

MemberContent
specThe spec name, zikaron/1
entryTypeThe type: genesis, history, grant, revocation, adoption, succession, annotation, or any agreed new type
authorThe author’s address, in lowercase hexadecimal
seqThe sequence number, from 0
prevThe ID of the entry before; null for the first
bodyThe body, by type
sigA 65-byte EIP-191 signature

An entry’s ID is the SHA-256 of all its bytes. The canonical form: compact, members sorted by bytes, integers in decimal, hexadecimal always lowercase. See law §3 and §4.

The command line’s ledger folder

A plain folder with one file per entry, each named with the entry ID’s 64 hexadecimal digits plus .entry. This is the folder zikaron writes; the reading subcommands also take ledger mirrors and record kits, see Command line. A strict read names a zero-length entry file.

The machine folder

One per machine. On macOS and Linux its default location is ~/.zikaron-desk.d/, and the pointer file ~/.zikaron-desk can point it elsewhere: one line holding an absolute path, ending in a newline, readable and writable by its owner alone; on macOS, with no pointer and an existing ~/Library/Application Support/ZIKARON, the app uses that folder. On Windows the pointer file and the default machine folder both sit in %LOCALAPPDATA%\ZIKARON\: .zikaron-desk and .zikaron-desk.d\. On every start the app writes the pointer to the machine folder it uses, keeping it as it is when it already points there; the command line finds the machine folder in the same order.

FileContent

On macOS and Linux the machine folder is found from HOME; on Windows, from USERPROFILE (the system’s user profile folder when it is unset): when that is the system’s user profile folder, in %LOCALAPPDATA%\ZIKARON\, and otherwise in AppData\Local\ZIKARON\ under it. The app uses its own key store alone and leaves the system keychain as it is.

Data folders

One for each role of each identity, by default inside the machine folder, with the role subfolder author (Recorder) or grantee (User). A data folder stores relative paths alone, so a copy anywhere else, or on another machine, reads back byte for byte. Inside are four subfolders:

ledger/
The ledger, one encrypted file per entry.
kits/
Exported record kits, grant files, credentials and snapshots, and the terms files kept at signing (kits/terms/).
grants-held/
Received grants, each with the verdict of its last re-verification; grant files received are in grants-held/files/.
settings/
Settings desk.json (with this data folder’s network, auto put on chain and “Hide entries deleted on this machine”), the pending queue queue.json, the last ledger check last-audit.json, the encrypted folder label home-label.json (this data folder’s random number, and which role of which identity it belongs to), the plain writer mark writer-mark (one line naming the machine that writes it), and the lock writer.lock that lets one window write.

Data folder names and the file names in the ledger are rewritten under a local names key, which keeps addresses and entry IDs out of the file names; contents are encrypted file by file. To let another tool read a ledger, export a ledger mirror.

The write lock is held by the operating system’s kernel and is let go the moment the process ends, power loss and forced quits included; it stays with the app’s own process, and programs started from the app run in processes of their own. A kernel lock covers one machine, so each data folder also has a writer mark: when it names another machine, or reads as something this version does not know, the window opens the data folder read-only, and rewrites the mark and takes over once you choose “Write from this machine”. Opening also reads the folder label first: a label belonging to another identity or role is refused, and that data folder is left as it is; a data folder an older version left gets its label from the first window that opens it as the writer.

Encryption of local data

The local data key is derived from the master key with HKDF-SHA256 (info string zikaron/local/v1), and the names key uses the info string zikaron/names/v1. Each file is encrypted on its own with XChaCha20-Poly1305, with a fresh nonce for every seal. The full standard and its test vectors are in the source at crates/app/local-data-standard.md.

{{code: "zikaron-local/2\n" · algorithm (1 byte) · kind length (1 byte) · kind · version (u16 big-endian) · identity digest (16 bytes) · nonce (24 bytes) · ciphertext and tag }}
Algorithm
2 is the one written: the second half of the identity digest is keyed. 1 holds that half as a plain digest, kept for reading.
Identity digest
A file’s identity is its owner and its place. A file in the machine folder belongs to machine; a file in a data folder belongs to that folder’s random number, kept in its folder label. The place is the kind plus the file’s logical name in its folder (which slot, which name), kept apart from its path and its name on disk, so after moving a data folder, renaming everything under a new master key, or restoring onto another machine, every file opens as before. The first 8 bytes open sha256("zikaron-local/owner" ‖ 0 ‖ owner); the last 8 open HMAC-SHA256(K, "zikaron-local/place" ‖ 0 ‖ logical name), with K derived from the local data key by HKDF-SHA256 under the info string zikaron-local/place-key. Matching a file head to an entry or grant ID therefore takes the key.
Associated data
The whole head, nonce included. A head with any byte changed, or a file moved to another place or another data folder, does not open. The plaintext repeats the owner and the logical name, and both are checked after opening.

The older envelope "zikaron-local/1\n" (kind and version as associated data) reads for good and stays as it is after reading. Writing uses the present envelope alone, and migration happens one write at a time: a file takes the new envelope the next time it is written, and a ledger entry stays as it was first written. Files this version writes are therefore read by this version and later ones, and earlier versions cannot read them; after upgrading, keep opening the same data with the new version.

A file that does not read is refused as LOCAL_SEAL, its detail naming one of six reasons: not-sealed (the magic missing), truncated (the head or the tag cut short), other-kind (sealed as another kind), newer-version (a later version or algorithm), swapped (another file: the digest differs from the one asked for, or the data folder lacks its label), unopenable (another key, or a byte altered). A file that does not read is left as it is: a write to it is refused by name; move the file aside and the next write makes it anew. Write-once files (held grants, kept grant files, terms files and issuance records, ledger entries) are refused whenever one is already there.

A write seals first, then lands through a temporary file renamed into place, mode 0600; on Windows, a rename that meets a file another program holds for a moment is retried within one second. Entries land on FAT and exFAT volumes as well. An older copy of the same file put back in its place goes unnoticed by the envelope; the ledger has its own signature chain.

The key store

The master key and each identity’s keys are sealed in keys-anchor.json: the passcode derives a key through scrypt (N=262144, r=8, p=1), encryption is AES-128-CTR, and a keccak MAC checks it. The passcode is 8 ASCII letters or digits; after 5 wrong tries in a row it locks, and recovery is the way on.

Whole-machine backups

File name zikaron-backup-YYYY-MM-DD.zikaron (UTC date); a second export on the same day is numbered -2, -3. The first line is zikaron-backup/1, and the second is a canonical JSON header: app, created, format, kdf (scrypt’s N, r, p and a 32-byte salt) and nonce. The body’s key is derived from the backup password with scrypt (N=262144, r=8, p=1), and the body is encrypted with XChaCha20-Poly1305, with the two header lines as associated data.

A backup holds the identity registry, each identity’s keys, every encrypted local file (opened, then placed inside), the record of the primary identity, machine.json and the read-only networks list (member readNetworks). The master key, the passcode and the wrong-try count stay on the machine; checked facts, the backup index, the data folders of deleted identities and plain exports (record kits, the index, verification result files, credentials, grant files, mirrors, key files) stay outside the backup too.

A backup writes to a free name alone: when its name is taken, it takes the next free number. It counts once it is read back and opened; a failed backup is recorded in machine.json as backup_failed. On restore, each member’s path is checked, and a member whose path climbs out of its place is refused; a restore makes a new master key; a backup carrying the read-only networks list replaces this machine’s list, and an older backup, which lacks one, leaves this machine’s list as it is.

Key files

A standard Ethereum keystore (V3): scrypt (N=262144, r=8, p=1) and aes-128-ctr, named UTC--<time>--<40-hex address>, mode 0600, encrypted with the file password set at export (at least 8 characters). After writing, the app reads it back and checks its format and address, and the export counts once they match.

On import both derivations read: scrypt, and pbkdf2 (hmac-sha256, 1 to 224 rounds). scrypt’s parameters must stay in bounds: memory 128·r·N at most 230 bytes, p from 1 to 16, total work 128·r·N·p at most 232 bytes; the key store and whole-machine backups read their parameters within the same bounds. A broken file, or one out of bounds, is refused before any derivation.

Record kits

A folder whose format is set by zikaron.kit/1 §7:

{{code: kit-3fa9c2e1/ manifest.json the manifest entries/<64 hex>.zk1 entries, one file each files/ original files and attachments files/verify.md verification notes for the receiver proofs/ on-chain proofs }}

The manifest lists every entry’s ID, every file’s path, size and SHA-256, and the transaction behind each proof; a file in the kit outside the manifest fails the check. The kit ID is the SHA-256 of the manifest’s bytes. Paths inside a kit use a-z, 0-9, ., _ and - alone; when attachments were renamed, files/zikaron-names.json maps original names to kit names, and the rename rule is <rewritten name>-<first eight of the original name’s SHA-256>.<extension>.

The exported folder is named kit- plus the first eight characters of the content fingerprint of the chosen record with the lowest sequence number; when the choice holds other entries alone it is kit, and a taken name is numbered -2, -3.

On export, a line naming the chain the kit is anchored on is added at the end of the manifest’s note note_md:

{{code: anchored-on: eip155: · registry · from }}

The separator is “space, · (U+00B7), space”, the same in every interface language, taken from this data folder’s network at the moment of export; with no network set, no line is added, and a note already ending in such a line has it taken off first. The line is a tool-layer convention, and the law still reads the anchors on chain alone: a check uses the line to say which network to add.

The record kit index

kits/index.json in the machine folder, format name zikaron.kits-index/1, kept plain so that other apps on the same machine can read it; see Integration. Each exported kit gets one row, and exporting again to the same path replaces that row:

FieldContent
idThe kit ID
createdThe moment of export, in Unix seconds
rootThe ID of the ledger’s creation entry
pathThe kit’s absolute path
contentsThe content fingerprints of the originals in the kit
note_mdThe note, as the author wrote it, without the anchored-on line
anchoredOnThe chain the kit is anchored on: {chainId, fromBlock, registry}, optional
linkThe fetch address (the kit’s https address online), optional

Verification result files

Each kit, grant file or publish address verified writes a result in the machine folder under kits/verified/, named 0x<sha256 of the kit’s manifest file>.json; verifying again replaces it whole. Its format name is zikaron.kit-verification/1, plain and owner-only, in canonical JSON:

{{code: {"anchors":[…],"at":,"basis":{…}?,"core":,"form":"zikaron.kit-verification/1", "kit":?,"kitVerdict":{"subject":"…"?,"verdict":"…"},"manifestSha256":, "missed":[{"chainId":…,"reading":"down"|"fingerprint","registry":"0x…"}], "records":[{"anchor":{"blockNumber","blockTimestamp","chainId","registry","tx"}|null,"content":}]} }}
records
One row per record in the kit: its content fingerprint and the earliest anchor counted for it; null for a record not on chain, or, when a chain could not be read, for one with no anchor on the chains that were read.
anchors
The anchors this pass found, each with its registry contract.
basis, missed
The chains read this time, and the networks not read with their reading code: down unreachable, fingerprint fingerprint mismatch.
core
The digest of the core that judged.

A kit that does not hold is written too, with its verdict alone; a kit that holds is left unwritten when no chain was read this time. The app writes the file and never reads it back, and the file changes no verdict; see Integrating.

Grant codes and credentials

The text zikaron-grant: followed by one or more segments joined by .. Each segment is a grant entry’s canonical bytes in base64url, padding left off; with several segments, they run from the original author’s grant to the current one. The whole is capped at 2,953 bytes, exactly the capacity of one QR code (version 40, byte mode, error correction level L). The format is in zikaron.kit/1 §6. A pasted grant code first loses its line breaks, spaces and invisible characters (zero-width characters, soft hyphens, byte-order marks), and is then judged by its shape: one of the wrong shape is refused by name.

A credential folder is named badge- plus the first ten characters of the grant ID; inside, badge.txt is the text as it is, and badge.svg is its QR code.

Grant files

Extension .zkgrant, named grant- plus the first ten characters of the grant ID. It is a container: the first line is zikaron-kit-file/1, and each item after it is written as “path in the kit, newline, decimal length, newline, bytes, newline”, the manifest first and the rest in byte order. A length reads in the encoder’s spelling alone: decimal digits, 0 for zero, and otherwise a first digit from 1 to 9. It is capped at 64 MiB in all and 4096 items. It is read in one place (zikaron_glue::grantfile), shared by the app and the command line’s check-grant. Inside are:

  • manifest.json;
  • entries/*.zk1: the entries of every hop in the grant chain, together with the issuer’s ledger when the grant is in this role’s ledger;
  • files/zikaron-grant.txt (the grant code), files/terms/… (the terms files), files/verify.md, and optionally files/publish.txt (the published address set in the data folder that exported the grant file).

Ledger mirrors

{{code: /ZIKARON-backup/<40-hex address>// mirror.json kind desk-mirror, version 1 entries/<64 hex> entry bytes, named by ID alone held/ received grants and so on }}

When the folder already holds an older mirror, only the new entries are added. The command line’s reading subcommands can point straight at the level holding mirror.json; to use it as a --ledger folder for the writing subcommands, copy the files in entries/ into an empty folder and add .entry to each file name.

Agreed literals

bytes-sha256/1
The mark of how a record was made, one for files, folders and Git repositories alike, meaning the content fingerprint is the SHA-256 of a run of bytes. For a file, the bytes are the whole file; for a folder, the canonical JSON {"files":[{"path":…,"sha256":…}…]} sorted by relative path (symbolic links and special files are skipped and counted, and an empty folder is refused); for a Git repository, the current commit object’s bytes without the commit <length>\0 header, the same as git cat-file commit HEAD | shasum -a 256. The toolchain paired with it is the SHA-256 of this literal itself: 0xb7f3c4a226684d6da684b0ac82d36ed5bcba7bb61d09c955bff9437f84a52a4d.
retraction
The type name of a deletion entry. In the body, subject is required: the ID of a record in this ledger, 0x followed by 64 lowercase hexadecimal digits; note_md is optional. Other tools list it as an unknown type (UNKNOWN_TYPE) and the ledger’s verdict stays as it was; this app’s reading lives in zikaron_glue::retraction, shared by the app and the command line.
for
An extra member in a record’s body: app, identity (hex20) and ref, with an optional seat. Once any of them is filled in, the first three are required.
upstream
An extra member in a grant’s body, holding the ID of the upstream grant; zikaron.kit/1 reads it as a sublicense.
